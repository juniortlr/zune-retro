## Material findings

1. EDD-01 tests protocol methods with fresh memory streams; it does not prove live accept-loop recovery. Several cases use malformed GUIDs and do not isolate the claimed version/enum behavior.
2. EDD-02 creates neither cold processes, a real fake pipe endpoint, nor a WPF window. Its ordering and HWND assertions are not falsifiable acceptance oracles.
3. The baseline wire reader constructs `ActivationRequest` directly and default JSON behavior is not a strict schema. The listener lacks connection-local containment for every parser timeout/fault and handler fault.
4. The baseline client validates only server session. The mutex uses default construction security; no readiness publication, descriptor read-back, bounded queue, or rate-limit proof exists.
5. The monitor snapshot returns only the primary monitor, and the application directly performs visibility/focus effects. Reducer, topology-change, monitor-removal, and prior-focus requirements are not established.
6. The earlier G1a description counted six 200-item groups and described 200 batches of five, contradicting the exact 1,000-case protocol.

## Design corrections

- Negative coordinates are valid in multi-monitor virtual space. Validate checked ordered bounds, positive dimensions, virtual-screen limits, and current-monitor/work-area intersection.
- Do not catch `Exception` indiscriminately. Classify expected connection-local failures and continue; treat requested shutdown normally; do not silently swallow fatal runtime failures.
- Supervision must expose unexpected listener completion promptly. Awaiting tasks only during shutdown is insufficient.
- Expected executable identity is defense in depth, not proof against same-user/same-session/same-integrity impersonation, which is outside the specified boundary.
- EDD-04 must specify supported object security, required rights, handle non-inheritance, endpoint checks, readiness, bounded queue/rate behavior, and recovery tests before selecting low-level APIs.
