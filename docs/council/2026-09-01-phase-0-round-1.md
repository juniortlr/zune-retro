# Phase 0 Council — Round 1

**Date:** 2026-09-01

**Scope:** Gate G0 and the Phase 1 feasibility sprint

**Method:** Independent Windows/.NET architecture, product/design/accessibility, and QA/security/release reviews followed by synthesis

**Decision:** **CONDITIONAL GO — documentation only until owner ratification**

## Consensus

All three reviewers agreed that the Start-only, Explorer-coexisting architecture is viable enough to test after owner ratification. None approved a public binary, a stable Start-replacement claim, or a formal G0 pass.

The owner must still ratify the charter and choose a source license or explicitly select all-rights-reserved development. Until then, the public repository is owner-only planning material that is visible to the public but is not an open-source release and does not accept contributions.

## Corrections accepted unanimously

1. `Win+Z` is not a viable default on Windows 11 because it belongs to Snap Layouts. A local `RegisterHotKey` probe returned error 1409 for `Win+Z`; `Ctrl+Alt+Space` registered and unregistered successfully.
2. Phase 1 uses a configurable, runtime-negotiated chord with `Ctrl+Alt+Space` as the first candidate. Registration failure is nonfatal; `EmberStart.exe --toggle` and native Start remain available.
3. `Ctrl+Esc`, not `Shift+Win`, is the documented native Start fallback. All operating-system Windows-key shortcuts remain untouched.
4. Phase 1 will not use a low-level keyboard hook.
5. The one-week spike starts with three runtime assemblies—Core, Windows, and App—not the full production assembly split.
6. Gate G1 has two outcomes: G1a proves a hotkey/command launcher; G1b proves the stable product promise through verified RetroBar Start-button invocation.

## Role findings

### Windows/.NET architecture

- Keep pure models, geometry, activation contracts, and protocol DTOs in `EmberStart.Core`.
- Keep Shell COM, Win32, monitor/DPI, hotkey, IPC, and launch adapters in `EmberStart.Windows`.
- Keep WPF lifecycle, composition, HWND/message handling, focus state, views, and token resources in `EmberStart.App`.
- Enumerate the Shell AppsFolder on a bounded STA worker. Preserve Shell identities and launch via Shell/PIDL or AUMID APIs; never rebuild command lines from display metadata.
- Use Per-Monitor v2, physical screen pixels at the IPC/Win32 boundary, and WPF DIPs inside the view.
- Spike a per-user full-trust MSIX app execution alias and compare it with a stable unpackaged per-user entry point.

### Product/design/accessibility

- Use the restrained Ember Fusion direction for the technical spike; compare it with the denser Ember Classic treatment at G2.
- Use a 704 × 640 DIP starting surface, an 8-DIP work-area margin, 44-DIP minimum rows, and a single-column fallback below 640 DIPs.
- Put search before the scrollable body and Power/Session plus Open Windows Start in the footer.
- Add `OnAccent`, `Selection`, and `OutlineStrong` tokens. Never place white text on the bright orange Accent; the contrast is insufficient.
- Phase 1 must expose a sensible UI Automation tree, keyboard navigation, Narrator announcements, contrast-theme resources, reduced-motion behavior, and 200% text resilience.

### QA/security/release

- Treat IPC, CLI input, Shell metadata, shortcuts, icons, imported state, and packages as untrusted.
- Restrict IPC to the current user and Windows session, authenticate the connected client, cap messages at 4 KiB, use finite timeouts, validate every placement field, and accept only a fixed command enum.
- Prove `asInvoker`, `uiAccess=false`, enforced medium-or-lower integrity, rejection of elevated-parent launches, no runtime elevation, and writes confined to per-user state.
- Forced termination must leave Explorer, RetroBar, and native Start immediately usable.
- Begin a reproducible native All Apps comparison ledger in Phase 1 even though the 99% completeness gate belongs to G3.

## Primary risks for the sprint

1. Foreground permission transfer from a secondary launcher or RetroBar to the resident menu.
2. Shell COM calls that stall, leak, or return incomplete identities.
3. Physical-pixel/DIP conversion before the first visible WPF layout.
4. Version-independent activation across package upgrade and rollback.
5. Incorrect trust assumptions around a same-user named-pipe client.

## Round 2 questions

The council must red-team the written G0 record and Phase 1 specification for:

- hidden scope expansion;
- unsafe or unsupported API assumptions;
- tests that cannot objectively prove their claim;
- missing accessibility or multi-monitor evidence;
- packaging/rollback claims that are not reproducible;
- inconsistent terminology between the master plan, ADRs, and gate packet.
